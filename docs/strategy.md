# strategy

## 現在のメイン戦略

初期段階では、まず検証可能なベースラインを作ることを優先する。
現時点では、噛み切りを使わない方針で進める。

## 方針

### 1. まずは全食べを安定させる

- 初期実装では、盤面をジグザグに走査して全ての餌を食べるベースラインを作る。
- この段階では色順の最適化よりも、`k = M` を安定して達成することを優先する。
- 手数 `T` の短縮は後回しにする。

### 2. 噛み切りは初期戦略では使わない

- 噛み切りは後半の再構成に使える可能性があるが、初期段階では挙動の理解と検証を優先する。
- まずは「噛み切りなし」でどこまで到達できるかを基準にする。
- 噛み切りの導入は、ベースラインとスコア計算の信頼性が確保できた後に検討する。

### 3. score 計算を先に固める

- 探索や改善に入る前に、最終状態から絶対スコアを計算する処理を実装する。
- スコア計算が正しいことを、手計算しやすいケースやベースライン出力で確認する。
- 改善判断は score を基準に行う。

### 4. simulator と実行手順を先に確認する

- `simulator.py` を実行し、出力に対する最終状態とスコアの確認手段を用意する。
- `README.md` に記載されているコマンドがそのまま動くか確認する。
- ローカル実験の手順を早めに安定化し、以後の改善サイクルを回しやすくする。

### 5. BFS の簡略化方針

- 初期版では噛み切りを使わない。
- したがって、経路探索では胴体を障害物として扱う。
- まずはこの単純化で `E` をどこまで減らせるかを確認する。
- 噛み切りを使う探索は後段で検討する。

## 当面の実装対象

- ジグザグで全ての餌を食べるベースライン
- 絶対スコア計算
- score 計算の正しさ確認
- `simulator.py` の実行確認
- `README.md` 記載コマンドの確認

## この戦略で見たいこと

- 噛み切りなしで `k = M` がどの程度安定するか
- ジグザグ全食べで `E` がどの程度出るか
- `T` よりも `E`, `M-k` の改善が支配的であることを実測でも確認できるか
- 今後の greedy 改善を行うための検証基盤が揃うか

## 次段階の入口

以下が確認できたら、次に色一致を意識した greedy に進む。

- ジグザグ解を常に生成できる
- `score()` の値を信用できる
- simulator の結果とローカル計算が一致する
- 実験コマンドが安定して回る
